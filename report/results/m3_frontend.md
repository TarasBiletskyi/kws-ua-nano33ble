# M3 — feature frontend

## Step 1 (2026-11-03) — `firmware/kws_nano33/frontend.c`, tested on the PC (V3)

Plain C99, no Arduino dependency, float32 arithmetic with double running sums in CMVN. Nothing was flashed; the board has not run this code yet.
The FFT is a real 512-point transform through a radix-2 complex 256-point FFT, with tables generated by `tools/export_tables.py`. `tools/build_frontend_pc.py` compiles the same file into a DLL with the MSVC compiler
that comes with Visual Studio (ScopeCppSDK, version 19.12), so nothing had to be installed. The frame gate and the DC blocker are not included yet; they belong to the microphone path at M4.

|---|---|
| Size for the board (`arm-none-eabi-gcc` 7.2, `-O3`, 0 warnings) | 11,680 B of flash including the tables |
| RAM | log-mel ring 15,524 B; stack in `fe_finish_window` ≈5.5 KB |
| Tests (`python -m pytest tools/tests`) | 26 passed, 5 of them new for this code: FFT vs NumPy, log-mel and features vs the specification, ring wrap, window readiness, digital silence |

**Digital zeros.** A clip of exact zeros has constant MFCCs, so CMVN divides rounding noise by ≈1e-8. Each implementation then gives different numbers, including the two references against each other. It costs nothing here, but it matters at M4: a
microphone never gives zeros, while the planned frame gate writes them. If the gate zeroes a whole window, the features are noise. The firmware must then skip `Invoke`, and the energy gate of the plan does that.

Not covered yet: the same code on the board's FPU (V2), its speed, the plan's V1 on 50 vectors and V4 over serial. JSON `v3_frontend_pc.json`.

## Step 3 (2026-11-03) — serial test server, V1 and V2 on 50 clips of 15 classes

`firmware/kws_nano33` in `KWS_TEST_MODE` 3 (`serial_proto.cpp`), `-O3`, driven by `tools/serial_harness.py` (pyserial). The PC sends audio or features with a CRC16, the board answers with its results. The 50 golden clips are stratified over all 15 classes.

| Comparison | Result |
|---|---|
| Softmax vs tf.lite 2.17 reference kernels | **bit-exact on 50/50 clips** |
| Top class vs tf.lite 2.17 | 50/50 |
| Softmax vs LiteRT 2.3.0 | bit-exact on 40/50, largest difference 10/256 |

| GAP vs LiteRT 2.3.0 | largest difference 3 |

**V1 passed**: the plan asks for a bit-exact match with at least one of the two PC runtimes, and the two runtimes also differ from each other (M0, knowledge base 04).

### V2: audio through the frontend and the model, `device_v2.json`

| Criterion | Limit | Result |
|---|---|---|
| Largest feature difference vs librosa | ≤ 0.05 | 7.0e-5 |
| int8 inputs identical, rest ±1 | ≥ 98 % | at least 99.97 % per clip, 45 of 50 clips 100 % |
| Top class vs PC (LiteRT 2.3.0) | ≥ 49/50 | 49/50, the same clip 5 |
| Top probability vs PC | ≤ 0.05 | 0.039 |

**V2 passed.** Timing over the 50 clips: 1.93 ms per frame, 46.9 ms per window, 1.970 s per `Invoke`.

### What the link taught

- **Large transfers.** Unbroken 32 KB transfers over USB serial lost their last 62 bytes, and once a port session started doing so it kept doing so; the cause was not identified. Blocks up to 3.8 KB never failed, so audio now travels in 2 KB blocks, each acknowledged by the board: 20/20 in one session, then all of V2. A CRC guards every transfer, so a loss cannot go unnoticed. This does not touch the microphone path, whose audio does not cross USB.
- **Reading.** Data must be read through `Serial`: the driver puts it into a 256-byte ring first, so bypassing the ring loses bytes.

All 1,204 test clips went over USB through `frontend.c` and the model on the board, about 2.7 s per clip, without a failed transfer. JSON `device_v4.json`, per-clip log `tools/out/m3/v4_clips.jsonl` (untracked).

**The 2 differing clips** had identical int8 inputs on both sides, so the difference comes from the two model runtimes rounding differently, not from the frontend: «два» is right on the PC and wrong on the board, and «так» is wrong on both. That one clip is the whole accuracy gap.

**Inputs.** On the 1,202 clips with sound the int8 inputs differ between board and PC by at most ±1, with 99.9988 % identical. The 2 clips of digital zeros differ widely, as on the PC (step 1), and are still classified as `_silence`.

**Per class** the board's recall equals the PC's except for that clip. The weakest class stays «так» at 85.1 %, mostly confused with «там» (12 clips), «зараз» (7) and «тут» (6).

**M3 is complete:** V1, V2, V3 and V4 passed. These are clean test clips with no microphone; the real microphone path starts at M4.
